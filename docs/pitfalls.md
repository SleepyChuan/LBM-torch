# 已知陷阱

按"踩了之后最难查"的顺序排。

## 数值

**壁面位置**。半程反弹的无滑移面在 `y = 0.5` 和 `y = Ny - 1.5`，
不是 `y = 0` 和 `y = Ny - 1`。把节点索引当坐标代进解析解，误差是
`O(dx)` 量级的系统偏移，而且看起来非常像"边界条件写错了"。
`Ny=16` 时这个偏移能让相对误差直接到 10%。

**Guo 的 `F/2`**。宏观速度必须写成 `u = (sum(f*c) + F/2)/rho`。
漏掉 `F/2` 的话稳态速度大约偏低一半；更麻烦的是 `feq` 和诊断
如果用了两个不同的 `u`，会出现"守恒量看着对、剖面就是不对"的情况。

**`(1 - 1/(2*tau))`**。Guo 源项前面的这个因子漏掉，程序完全正常、
完全稳定、完全没有 NaN，只是稳态速度系统性偏低，且偏低量随 `tau` 变化。
只用单一 `tau` 验证是发现不了的——必须换一个 `tau` 再跑一次。

**`tau = nu/cs^2 + 0.5`**。那个 `0.5` 经常被漏。用 `tau = 3*nu` 也能跑，
而且看起来"差不多对"，但粘度实际上错了 3 倍。

**`nu` 的符号**。构造时校验 `nu > 0`。`nu = 0` 会让 `tau = 0.5`，
碰撞变成纯覆盖，数值上立刻发散。

**稳态时间**。粘性扩散时间大约 `H^2/nu`。`H=14, nu=0.1` 时是 1960 步，
跑 200 步看到的"抛物线"其实还带着初始瞬态，误差会到几十个点。
不要用跑的步数太少来解释对不上的结果。

**收敛测试的马赫数**。加密网格时如果固定 `F`，`u_max` 会按 `H^2` 长，
`Ny=64` 时 `Ma` 已经 0.68，测到的是压缩性误差不是格式误差，
误差不降反升。要固定 `u_max`，让 `F ∝ 1/H^2`。

**固体节点上的垃圾值**。固体节点不碰撞、不更新，pdf 保持初值 0。
如果初值填了 `NaN`，`where` 会丢弃它，看起来没问题；但只要有任何一个
地方对全张量做了 `sum` 或 `mean` 才发现不了，就会出现"总质量是 NaN"。
初值统一填 0，不要填 NaN。

## PyTorch

**`cur_idx` 会产生两份编译图**。`torch.compile` 对 Python int 做特化，
0 和 1 各一份，这是正常的，缓存稳定在 2 个变体。别为了"只编一次"
把它改成 tensor 索引——那要多一次 gather。

**不要用布尔索引**。`f[mask]` 需要知道 `mask` 有多少个 True，
会触发 device→host 同步，性能直接崩。要改就预计算长整型索引张量。

**不要在循环里 `.item()` / `.cpu()` / `.numpy()`**。每调一次就是一次同步。
判断 `loss < tol` 之类的逻辑，要么放到循环外，要么接受它每 N 步才做一次。
`diagnose()` 里可以同步，因为它本来就是一个"停下看一眼"的操作，
但它不能在 `_step_once` 里。

**`inference_mode`**。整个 `step()` 外面套 `torch.inference_mode()`。
不做的话 autograd 会记录图，显存直接翻倍，MPS 上尤其致命。
但注意 `initialize()` 里要写 buffer，用 `no_grad` 或者确保在
`inference_mode` 作用域内做的是 `copy_` / 原位写。

**热循环里不要新建张量**。`(Q,1,1)` 的 `c`、`w`、`opp` 索引、`wall_mask`
全部在 `__init__` 里建好。在 `_step_once` 里 `torch.tensor([...])` 一次
就是一次 host→device 拷贝。

**`.to(dtype)` 的位置**。保存时顺序固定为 `detach().cpu().to(np_dtype)`。
MPS 上先 `float16` 再 `cpu()` 有时会报不支持的操作。

**in-place 写要小心别名**。`dst[i, 1:, :] = f_post[i, :-1, :]` 这种写法，
如果 `dst` 和 `f_post` 是同一块内存（忘了用双缓冲）会得到撕裂的结果，
而且不报错，只是曲线慢慢变形。单测里加一条 `assert dst.data_ptr() != f_post.data_ptr()`。

## 平台

**MPS 不支持 float64**。构造时如果 `device == "mps"` 且 `compute_dtype == float64`，
直接报错。想做高精度对照，就把算例挪到 CPU 上跑。

**M2 8GB 是统一内存**。8GB 要和系统共用，实际可用于 tensor 的大概 4~5GB。
`D2Q9` 在 `2048x2048` 上双缓冲是 `2*9*2048*2048*4 ≈ 300MB`，
不算大；但 MPS 的内部缓存不会立刻归还，连续开多个 solver 容易 OOM，
用完记得 `del` + `torch.mps.empty_cache()`。

**MPS 上 `torch.compile` 支持有限**。开启后如果报 Triton 相关错误，
按用户要求直接抛出去，不要吞掉。把"这台机器上编译不可用"这个结论
记在这里，别每次重新试。

**CUDA 上 4060Ti 是 8GB**。`512^3` 的 D3Q27 双缓冲要 7.2GB，
放不下。D3 的规模上限先按 `256^3` 算：`2*27*256^3*4 ≈ 3.6GB`，勉强。

**Windows + triton-windows**。这是个第三方分发，版本必须和 torch 严格对齐。
`pip install triton` 在 Windows 上装的是另一个东西，装完 torch.compile 会报
找不到 triton。锁定 `triton-windows` 的具体版本，写进 README。

## 性能

**MLUPS 的定义**：`Nx*Ny*steps / 1e6 / 秒`。报告性能时必须写清网格大小
和是否含编译时间，否则数字没法比较。

**带宽上限**。D2Q9 每节点每步理论最少 `9*4*2 = 72` 字节。
4060Ti 约 288 GB/s，上限约 4000 MLUPS。纯 PyTorch 逐方向切片会是这个
数的几分之一，`torch.compile` 能拉回来一些，但拿不到理论值。
不要对着 4000 去优化，目标定在 300~800 MLUPS 比较现实。

**M2 上别急着优化**。MPS 后端的 kernel 质量和内存带宽都有限，
在 M2 上调优得到的结论不能迁移到 CUDA。性能工作放到 P8 再做。

**`diagnose()` 不要每一步都调**。它要同步、要归约，成本远超单个时间步。
按用户的循环写法，每 `save_interval` 步调一次正好。

## 设计

**方向编号**。`i=1` 是 `+x`，`i=2` 是 `+y`。一旦这个顺序和 `opp` 表、
和切片逻辑对不上，`Poiseuille` 的 `ux` 和 `uy` 就会互换，
表现为"抛物线出现在错误的方向上"。这是最初的 P3 不动点测试能抓到的。

**忘记翻 `cur_idx`**。表现是所有东西都正常，但流场卡住不动，
因为一直在读同一份被写过又没被读的 buffer。

**保存了错误的 buffer**。`save_npz` 要存 `pdf[self.cur_idx]`，
即"当前时刻的分布函数"。存 `1 - cur_idx` 会得到上一时刻的场，
看起来很接近（差一步），只有做严格对比时才发现对不上。
